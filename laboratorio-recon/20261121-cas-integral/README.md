## Progresso executável local

1. `migration-CAS-LAB.sql.gz.b64`: SQL definitivo do experimento comprimido em base64; o script de teste descompacta só em memória e confere SHA-256 `c4a28b0758494c6be97064664bd0038224e7b03486f8afa93b9ed91b54f2d9d8`. Não usar o arquivo `.sql` anterior da branch: é apenas uma versão inicial, substituída. Dentro de uma única transação e sob locks exclusivos, compara os nomes das colunas conhecidos, aborta tabelas nmm desconhecidas, habilita RLS e troca políticas por leitura do dono, remove privilégios públicos de escrita e de coluna, verifica grants efetivos, revoga EXECUTE de TODAS as funções/procedimentos em public e aborta grants herdados. Também aborta funções SECURITY DEFINER executáveis de fora de public, views legíveis não revisadas, tabelas/colunas externas graváveis, usuário membro de papel superuser/bypass ou dono, e triggers não revistos. O corte derruba também funções public legítimas; é deliberadamente conservador, não é implantação. Abortos revertem a transação inteira.

2. CAS por registro para 12 entidades: tarefas, etiquetas, comentários, links, notas, logs, lançamentos, estado financeiro, transações bancárias, preferências, cofre e notas privadas. Usa uid da sessão, revisão monotônica, conflito sem retornar dados de outro dono, bloqueio de linha, preserva created_at nas atualizações, rejeita colunas desconhecidas e dono/chave fornecidos no payload, verifica dono da tarefa-pai e permite campos ausentes sem zerá-los. A escrita direta antiga e o EXECUTE de RPCs antigos são negados no modelo testado. Não há exclusão física, recibo idempotente, reconstrução/restore ou transação entre múltiplas linhas.

3. `test-CAS-isolado.py`: PostgreSQL 17 efêmero, socket privado sem TCP, usuários e dados fictícios. `python3 laboratorio-recon/20261121-cas-integral/test-CAS-isolado.py`. Testa hard stop, reversão completa em privilégio de coluna/RPC herdado, rotina antiga SECURITY DEFINER, função externa, view perigosa, tabela externa gravável, tabela e coluna não revisadas, dados legados de etiqueta preservados, 12 entidades criação/alteração, RLS A/B, tentativa de spoof, sessão ausente, parentesco, versão vencida e duas sessões concorrentes em nota. Testa alteração apenas de uma linha por vez. A definição bancária é FICTÍCIA e inferida de `app.js`, porque seu DDL não está no repositório; não é o catálogo real.

## Bloqueios críticos para fechar antes da integração

1. O SQL continua deliberadamente desativado: o catálogo Supabase real, chaves, políticas, papéis, permissões, triggers, todos os schemas, views, RPCs, extensões e service-role/importadores **não foram consultados nem validados**. A lista de nomes de colunas não valida tipo, constraints, FKs, dono da função `auth.uid()`, segurança de search_path de dependências, índices, row security forçada, chamadas transitivas, privilégios concedidos depois da migração, REPLICA/DDL ou todos os caminhos capazes de escrever. Uma role privilegiada externa pode contornar a proteção ou alterar dados sem avançar revisão. Revisar e cercar esses caminhos e permissões de funções futuras com default privileges; não usar este código com dados reais.

2. `nmm_bank_transactions` é conhecido pelo app, não há DDL versionado; schema, índice e regras de negócio são inferidos. O backend atual de importação pode gravar usando credenciais privilegiadas ignorando CAS. Não existe evidência de migração segura para essa entidade real; ela precisa ser reconciliada com quem cuida de finanças. CAS por registro não protege transferências, balanço, pagamentos, recorrência ou operações multientidade.

3. O SQL corta clientes antigos e altera RLS, por isso o app atual quebra; clients antigos com dados offline podem ter alterações pendentes. Não existe handshake por versão, plano de sincronização, drenagem/backup/restauração verificados, export de dados pendentes por conta, retenção, migração de estados locais por abas, revisão de tipos/constraints ou rollback de rollout. O experimento de revisão inicial 1 apenas preserva uma etiqueta legada sintética; não prova migração segura da base.

4. Ausentes: idempotência e recuperação de resposta perdida, tombstones/remoção, migração dos demais tipos de dados legados reais, validações relacionais completas de tags/notas, testes de concorrência para cada entidade e migração simultânea, testes de PostgREST, Supabase, Realtime, offline, múltiplas abas e navegador. O teste de CAS usa `request.jwt.claim.sub` sintético e não valida autenticação JWT real. Uma mudança posterior de schema pode tornar novas colunas implicitamente graváveis pela função: exige controle de DDL e allowlists explícitas por versão.

5. Ao integrar: identificar catálogo/escritores em ambiente de homologação sanitizado; fechar e testar caminhos privilegiados, reconciliar cada schema e o trabalho financeiro; criar API de operações idempotentes e transações multientidade; atualizar todos os consumidores e migrar alterações offline preservando backups; validar primeiro por testes adversariais completos e só então preparar corte coordenado reversível. Não fazer deploy nem executar SQL em produção neste estágio.
